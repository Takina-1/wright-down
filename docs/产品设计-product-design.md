### F004 导出与备份恢复（2026-10-29）
- 双产物：JSON 完整备份可恢复，Markdown 只供阅读不反向导入。
- 文件交付用系统文件选择器（SAF）保存到用户自选位置，并可发起系统分享；不申请运行时权限。
- 依赖按用途拆分：`file_selector` 读文件、`file_picker` 写文件、`share_plus` 系统分享、`path_provider` 临时目录；`file_selector` 在 Android 上没有实现保存接口，因此保存另用 `file_picker`。
- 恢复采用合并：按条目 ID 比 `updatedAt`，旧的不覆盖新的不丢失，重复导入幂等。
- 备份为明文，安全性依赖用户自选的存放位置；本次不做加密与口令。导出页与「我的 → 本地数据说明」都写明明文事实，用户自行决定存放位置。
- 备份格式带 `format` 与 `version`，将来加入附件或删除标记时递增 `version` 并保持旧版本可导入。
- 分享用的临时明文副本用完即删：写新副本前清掉同前缀旧副本，分享调用返回后删掉本次副本；分享过程中不提前删，由 `share_plus` 先把文件复制到插件自己的缓存目录。
- 备份条目的 `dayKey` 必须是 `YYYY-MM-DD`，格式非法的备份整体拒绝导入；界面对历史脏数据退回用创建时间的本地年月，不让时间轴崩溃。
- 范围与验收标准以 [功能需求](features/F004-导出与备份恢复-export-and-backup.md) 为准。

### F005 删除记录与回收站（2026-10-30）
- 删除一律是**软删除**：条目标记删除时间后从时间轴隐藏，数据仍留在本机。删除入口在**回顾页长按**与**记录页编辑态**两处，都要有二次确认，确认框里给出正文摘要。
- 提供**回收站**（「我的 → 回收站」）：可恢复、可彻底删除、可清空。回收站不自动清理，条目一直保留到用户手动处理。
- **软删除**的条目保留 `deleted_at` 墓碑，所以导入旧备份**不会**让它复活；合并判定对「本地已删除 + 备份未删除」无条件跳过，不看 `updatedAt`。
- **彻底删除**没有墓碑（物理移除），因此导入彻底删除之前导出的旧备份时该记录**仍会重新出现**。界面文案按此事实写明，不宣称「彻底删除后无法通过备份找回」。
- 备份格式随删除功能升到 `version: 2`：条目可带 `deletedAt`，`version: 1` 的旧备份仍可导入，`version` 高于 2 拒绝并提示升级。
- 软删除与恢复写入的 `updated_at` 取 `max(当前值, now)`，版本戳只许增不许减：设备时钟回拨时，刚恢复的条目不会被更旧的备份打回删除状态。
- 数据库 schema 升到 2（`entries` 加可空列 `deleted_at`），迁移必须**幂等**——用户用旧版打开过会让 `user_version` 被悄悄改回 1、表结构保留，不幂等会让整库永久打不开。
- 删除失败与保存失败分开：删除错误走独立的出口，不复用保存状态，否则界面会同时显示「保存失败」和「重试保存」。
- 范围与验收标准以 [功能需求](features/F005-删除记录与回收站-entry-delete-and-trash.md) 为准。

### 1. 定位
- **B（回顾）+ C（语音）** 组合
- B 管留存（写进去是为了以后回来看），C 管入口（说话代替打字，30 秒记完）
- 差异化不在"功能全"，在别人不愿做的脏活

### 2. 架构：Local-First
- 本地库是唯一真相源，服务器只做同步管道
- 三条铁律：
  1. UI 层不直接碰 RemoteRepo
  2. 写入只走 LocalRepo，同步是异步旁路
  3. Domain 层不 import 任何框架/SDK

### 3. 语音链路：端侧录音 + 云端转写 + 本地双写
- 端侧 ASR 先转写 → 文本立刻入库（保证离线可写）
- 音频上传 OSS（私有 bucket，预签名 URL）
- 云端 ASR 异步精修 → 用户确认后替换
- 字段：`content` / `rawTranscript`(本地) / `audioUri`(本地) / `cloudAudioKey` / `cloudTranscript` / `transcriptSource`
- 同步只传 `content` + `cloudAudioKey` + `cloudTranscript`
- 分段规则：显式「下一条」按钮 + 静默超时（默认 12 秒）双信号，每段独立 Entry
- 权限时机：点击录音按钮后才申请麦克风；拒绝后给打字替代路径，绝不反复申请

### 4. 同步引擎
- 单一写入口 + dirty_queue，脏队列按 updatedAt 顺序重放
- 增量协议：`GET /sync?cursor=<seq>` 拉取，`POST /sync/batch` 推送
- 冲突：**字段级 LWW**，每字段单独存 updatedAt，绝不整条覆盖
- 删除也要带时间戳：`{v: null, t: ts}`，不能用「key 不存在」表示
- 图片：sha256 秒传 → 预签名 URL 直传 OSS → 库里只存 key
- 软删（deletedAt）+ 同步删除标记

### 5. 回顾模块
- v1 集合：时间轴（Keyset 游标分页）+ 随机一篇 + 连续天数 + 热力图
- ReviewEngine 纯函数（`List<Entry>` → `List<ReviewCard>`），不依赖 UI/DB
- 主视图是垂直时间流，日历热力图放统计页做辅助
- 查询用冗余 `dayKey` 字段（`"2026-10-23"`）命中索引

### 6. 录音上云的合规要求
- OSS 必须私有 bucket，音频访问单独鉴权（不能拿到日记列表就能拉所有音频）
- 首次启动隐私政策弹窗 + 首次点录音**单独同意弹窗**（不可合并）
- 设置里提供「云端同步录音」开关，可随时关闭
- 全部存储于中国大陆境内；转写用国内厂商（阿里云/腾讯云 ASR），不用 OpenAI Whisper
- 隐私政策必须写明：存储期限、删除机制、是否用于模型训练

### 7. 账号体系
- **本地身份四态**：匿名(本地) → 已注册未登录 → 已登录 → 登出
- **账号只是"绑定"，不是"容器"**：本地库不按 userId 分库分表，userId 只是 Entry 上的一个字段
- **可跳过注册** ✅（用户想纯本地用随时可绑，避免流失）
- **注册方式：手机号 + 邮箱都可**（v1 建议先做手机号短信）
- **登出 ≠ 注销**：登出保留本地+云端数据；注销需二次确认并明确告知永久删除
- **认领机制**：注册后询问「要把本机 23 篇日记同步到云端吗」→ 是则批量改 userId 入 dirty_queue（是上传，不是下载合并）
- Device 表：设备列表 + 可踢设备 + 未来做免费版设备数限制
- 隐私政策：手机号不二次展示；注销入口在设置页一级菜单；注销后数据删除时限写明

### 8. 账号找回 ✅ 要做
- **找回链路**：手机号/邮箱 → 验证码 → 直接重置密码（不需要旧密码）
- **重置后必须吊销该账号所有 Refresh Token**，强制其他设备重新登录
- **设备信任链**：新设备登录时，旧设备在线则推送「有新设备登录，是否允许」；旧设备离线 → 允许登录但在「登录历史」展示，用户可自行踢掉
- **风险控制**：同手机号 60 秒 1 条短信；同 IP 10 分钟内最多 5 次找回；连续验证失败 5 次 → 锁定 30 分钟
- **行为检测**：非常用 IP / 凌晨大量尝试 / 同账号多地同时找回 → 标记可疑，加严验证
- **通知**：任何密码重置、任何新设备登录 → 立刻短信/邮件通知用户
- **多因素兜底**：手机 + 邮箱都绑 → 两个都能找回；只绑一个 → 只能用一个
  - ⚠️ 手机号失效 = 账号永久失联 → 绑定界面提示「建议再绑一个邮箱作为备用」；设置里做「账号安全」页展示绑定与缺失项
- **找回后的数据缺口必须说清**：UI 提示「云端日记会完整恢复，旧设备上尚未同步的内容无法找回」
- 隐私政策需写明：找回过程收集验证码/设备信息/IP，用于身份核验

### 9. 服务端
- **服务端 = dumb store + merge logic**，不做业务逻辑
- **游标用服务端单调递增 seq（BIGSERIAL），不用时间戳** ← 关键设计
- 每次写入/合并都赋新 seq，保证其他设备能拉到
- Entry 用 JSONB payload 存字段级 `{v, t}`，加字段无需 migration
- 部署：单机 + Docker Compose（Postgres + API + Nginx），OSS 托管，不上 K8s
- **API 只有 4 个**：`/auth/register`、`/auth/sms`、`/auth/login`、`GET /sync?cursor=N`、`POST /sync/batch`
- 认证：Access Token 30 天 + Refresh Token 90 天滑动续期；token 存 Keychain/Keystore（不存 SharedPreferences）
- 备份：Postgres 每日 pg_dump → OSS，保留 30 天；每月手动完整导出。⚠️ 备份数据也要境内，注销时含备份一并清除
- **所有回顾/统计/随机/热力图 100% 客户端算**，服务端永远不读用户内容
- 成本：轻量 2核4G ~100元/月 + OSS ~50 + 短信 0.04/条 + 域名 ~100/年 ≈ **150 元/月**

### 10. SyncEngine 状态机 ✅ 同意建议
- **三个独立循环**：写循环（用户驱动，最高优先级，永不失败）/ 推循环（后台）/ 拉循环（后台）
  - 写循环与推拉完全解耦：用户写日记永远不等网络
- **触发时机**：App 启动、进入后台、回到前台、写完延迟 30 秒、网络恢复、定时每 5 分钟、手动下拉
  - 「延迟 30 秒推」避免每写一条就发一次请求，攒批推送
- **重试策略**：2→4→8→16→32 秒指数退避 + 0~1 秒随机抖动；第 6 次放弃本轮，等下个触发点
  - 可重试：网络超时、5xx、429（退避更久，60 秒起）
  - 不可重试：403（账号/设备被踢）、400（格式错，是 bug 记日志）
  - ⚠️ 401：先用 refresh_token 换新 access_token 重试一次；再失败 → 停止同步 + 提示重新登录，**本地数据仍可用**，绝不自动登出
- **cursor 只在数据成功落库后推进**，与落库在同一事务里提交（原子性）
- **脏队列**：推送成功后移出；失败一直留，最长保留 90 天
- **合并**：每批 50 条短事务，避免长事务锁库；用户写入走独立事务互不阻塞
  - SQLite 开 `PRAGMA journal_mode = WAL` + `busy_timeout = 5000`
- **同步状态 UI**：⟳ 同步中 / ✓ 已同步（显示最后同步时间）/ ⚠ 同步失败（点开看原因 + 手动重试）。❌ 不静默失败
- **手动上传/下载按钮**：只在同步失败提示里给，不常驻

### 11. 界面信息架构 ✅ 同意建议
- **底部 3 Tab**：`✍️ 记录` / `📖 回顾` / `⚙️ 我的`
  - 记录固定在第一位；Tab 不超过 3 个（超过用户记不住）
- **记录页（首页）= 纯输入页**
  - 打开即聚焦，键盘自动弹起（省一次点击）
  - 占位符用**问句**（"今天想记点什么？"），不用指令式
  - 4 个可选快捷动作：😊心情 / 🎤语音 / 📷拍照 / 🏷标签 —— 每个**一次点击直达**，不嵌套二级页
  - 写完**自动保存**（停输 1 秒落库），无保存按钮；退出有未保存内容才提示
  - ⚠️ 不在首页放标题输入、日期选择器、心情标签云 —— 全部下沉二级
- **回顾页**
  - 顶部 2 张卡片：「🎲 随便看看」（随机一篇）+「🔥 连续天数」
  - 下方是时间轴（无限滚动 + 游标分页），按月分组
  - 搜索放顶部图标，**不做成 Tab**（低频需求）
- **我的页**
  - 账号状态卡（未登录时显示「未登录（本地模式）→ 登录后可多设备同步」）
  - 分组：同步 / 数据 / 隐私 / 关于
  - ⚠️ 三个必须一级可达（审核会查）：**注销账号**、**隐私政策**、**权限管理**
- **二级页面 11 个**：日记详情编辑、录音界面、标签管理、搜索结果、统计、登录注册、找回密码、设备管理、导出与备份恢复、隐私政策、账号安全
  - 心情选择用底部弹层，不做页面
- **全局交互约定**
  - 危险操作二次确认，删除类明确写"不可恢复"
  - 返回时有未保存内容 → 弹「放弃修改 / 保存」
  - 列表加载用骨架屏，不用转圈；按钮内联小转圈
  - 每个列表都要有空状态（插画 + 一句话 + 一个行动按钮）
  - Toast 在底部 Tab 上方，不遮挡操作区

## 三、架构草稿

```
┌─────────────────────────────────────┐
│  UI 层（页面 = 纯函数，状态来自 Store）  │
├─────────────────────────────────────┤
│  Domain 层（纯逻辑，零框架依赖）         │
│    useCase: 写日记 / 生成回顾 / 同步      │
│    review/ReviewEngine                │
├─────────────────────────────────────┤
│  Data 层                              │
│    LocalRepo(SQLite)  RemoteRepo(HTTP) │
│    └── SyncEngine（唯一写入口）          │
├─────────────────────────────────────┤
│  Platform 层（ASR/相机/通知/存储）      │
└─────────────────────────────────────┘
```

**数据流向**：回顾/统计/随机/热力图 100% 客户端算；云端 ASR 异步；服务端永不读用户内容。

## 五、软著 / 备案的隐性约束（影响设计）

- 软著名称 = 应用名称 = 备案名称 = 安装包内名称，**四者必须一致**
- 小米规定：应用名**每年只能改 2 次**，改名要重新提供软著
- **首次提交应用不要随便删除**，删了会冲突，之后要走「应用认领」流程
- OPPO 需要额外的**免责函**（其他平台不要）
- 硬性前提：**个人开发者无法上架 Android APP**，需企业/个体工商户主体
