# 开发流程与文档命名规范

适用范围：本项目从需求、参考调研、开发到测试、验收与发布的日常工作。

## 1. 流程规模

- 新功能或影响数据、权限、同步的改动：建立功能文档，完成后形成测试报告。
- 普通功能在一份功能文档内写清需求、方案、任务和测试计划，不强制拆成多份文件。
- 错字、排版、简单文案等低影响修改：记录改动与验证结果即可，不要求新编号、完整方案或自动化测试。
- 修复已有功能的缺陷：优先记录到原功能文档和测试报告，先复现，再修复并验证；独立且范围较大的改动可分配新编号。
- 用户已明确要求且范围清楚的工作直接推进。只在影响产品行为的关键决策确实缺失时提问，不按每个步骤重复要求批准。

## 2. 从需求到交付

| 阶段 | 要做的事 | 留下什么 | 可以进入下一步的条件 |
|---|---|---|---|
| 需求整理 | 写明用户场景、范围、不做什么和可观察的验收标准 | 功能文档第 1–3 节 | 没有阻塞实现的关键歧义，已明确本次授权范围 |
| 方案与参考 | 查功能参考索引，定位必要源码，决定数据流、异常处理和接口边界 | 同一文档的参考记录、方案与测试计划 | 明确改哪些模块、怎么验证，参考事实与假设分开 |
| 任务拆分 | 拆成可验证的小任务，标出依赖 | 同一文档的任务表 | 每项任务有结果和检查方式 |
| 开发自检 | 按任务实现，保护已有改动；必要时先写能复现问题或约束行为的测试 | 代码、任务勾选、实际方案变化 | 构建及本次改动适用的检查通过，可交给测试 |
| 测试修复 | 按验收编号执行自动化与手动测试，记录缺陷，修复后重测相关范围 | 测试报告 | 必需用例通过，无未解决的验收阻塞问题 |
| 验收归档 | 对照范围检查交付物、测试证据、文档和已知限制 | 更新台账并链接最终报告 | 满足下方完成标准；需用户体验确认的项目已有明确反馈 |
| 发布 | 在确定版本后检查构建、迁移、备份、隐私与上架材料 | 版本发布记录 | 发布范围和必需检查完成，具备当前会话所需发布授权 |

功能开发完成不等于已发布；测试通过不等于应用市场审核通过。

## 3. 功能编号和状态

- 新功能从 `F001` 开始递增，在 [功能任务台账](features/README.md) 登记。编号一经分配不复用，名称使用简短英文主题。
- 状态在台账统一维护：`待明确 → 待开发 → 开发中 → 待测试 → 待验收 → 已完成`。
- 关键依赖未满足时标为 `阻塞`，说明原因与恢复条件；取消的功能保留记录，标为 `已取消`。
- 测试发现问题回到 `开发中`，修复后重新进入 `待测试`。未执行测试不写“通过”，等待真机或用户体验时不写“已完成”。
- 功能文档包含需求与方案，测试报告包含证据，彼此通过同一个编号追踪。

## 4. 文件命名

统一使用英文小写单词和连字符；功能编号 `F001`、固定入口 `README.md` 与 `AGENTS.md` 例外。中文用于标题和正文。

| 类型 | 位置与命名规则 | 示例（仅示例，未立项） |
|---|---|---|
| 稳定的项目级文档 | `docs/<明确主题>.md` | `product-design.md`、`development-workflow.md` |
| 功能需求、方案与任务 | `docs/features/F编号-主题.md` | `F001-entry-autosave.md` |
| 功能测试报告 | `docs/test-reports/F编号-主题-test-report.md` | `F001-entry-autosave-test-report.md` |
| 大型功能需独立的详细计划（可选） | `docs/features/F编号-主题-plan.md` | `F004-cloud-sync-plan.md` |
| 发布记录（发布时创建目录） | `docs/releases/v版本-release-notes.md` | `v0.1.0-release-notes.md` |
| 模板 | `docs/templates/用途-template.md` | `feature-spec-template.md` |

- 同一功能在需求、计划、测试报告中使用相同编号和主题，不另起别名。
- 长期维护的文档不在文件名中堆日期，正文记录更新时间。测试每一轮注明日期与被测版本，保留历史结果。
- 不使用 `notes.md`、`new.md`、`final.md`、`test1.md` 等无法辨识用途的名称。
- 未来采用 Git 后，分支可使用 `feat/F001-entry-autosave`；提交示例为 `feat(F001): add local autosave`。当前不假定仓库已初始化。

## 5. 需求与验收标准怎么写

每条验收标准使用功能内编号 `AC-01`、`AC-02`，描述前置条件、操作和可观察结果，避免“体验良好”“基本可用”等措辞。

示例：

> AC-01：未登录且处于飞行模式时输入一段文字；按已确定的保存策略落库后关闭并重新打开应用，正文仍完整存在。
>
> AC-02：模拟本地写入失败时，不显示“已保存”；保留当前编辑内容，展示失败原因和重试入口。

保存延迟、恢复范围和异常行为要在开发前说清，不能把“永不丢数据”等无法保证的口号当验收标准。任何超出本次范围的新需求先记录，再决定是否纳入。

## 6. 如何参考开源项目

1. 在 [功能参考索引](feature-reference-index.md) 选择首选仓库，只查本次相关模块。
2. 需要借鉴具体逻辑时记录提交 SHA、源码永久链接、关键流程与异常分支。
3. 写出与本项目数据模型、平台依赖和协议的差异，再决定采用方式。
4. 直接复用源码时核对具体代码及依赖、模型、素材许可，保留所需声明。
5. 本项目的验收标准独立验证。README 声明的能力、源码存在和实际运行通过是三个不同状态。

## 7. 测试分层与执行记录

| 测试类型 | 适用内容 | 本项目的重点 |
|---|---|---|
| 单元测试 | 可独立执行的业务规则 | 连续天数、日期边界、字段合并、转写覆盖保护 |
| 集成测试 | 模块之间的实际协作 | 数据库事务、迁移、脏队列、cursor 提交、备份恢复 |
| 界面或端到端测试 | 关键用户路径 | 新建→保存→回顾→编辑，拒绝权限后继续打字 |
| 真机手动测试 | 平台、硬件和系统生命周期 | 录音中断、后台切换、系统权限、离线识别、低端机表现 |
| 发布前回归 | 本次受影响路径及核心流程 | 数据恢复、同步删除、隐私入口、升级兼容 |

- 测试验证用户行为或可靠性边界，避免仅重复实现细节。不同改动选择必要的层级，不强制每个功能跑满所有层。
- 报告至少包含被测版本、环境、命令或步骤、预期与实际结果、验收编号、失败项及未测范围。
- 测试结果使用 `通过／失败／阻塞／未执行`。模拟器检查不替代需要真机确认的行为。
- 先运行与改动相关的检查；只有新修改、失败或未解决风险需要时再扩大或重复测试。
- 当前技术栈未定，不能预写假定可用的构建或测试命令。初始化工程时把实际命令补到根 README，并在报告记录实际执行结果。

## 8. 完成标准

- 本次范围内的验收标准均有对应证据；未通过的必需项不能标为已完成。
- 适用的构建、静态检查、自动化及手动验证通过，阻塞缺陷已修复。
- 数据、权限、删除和失败恢复等受影响路径完成针对性检查。
- 实际实现与方案一致，变更和已知限制写清；影响产品设计时已同步更新。
- 功能台账链接到需求和测试报告；没有遗失的待办被“完成”状态掩盖。

允许验收包含明确约定的非阻塞限制，但必须记录由谁、何时接受，不得自行把失败项改成通过。

## 9. 发布记录最少包含什么

发布时创建 `docs/releases/v版本-release-notes.md`：版本号、日期、代码版本、构建产物标识、本次功能编号、关联测试报告、升级与数据迁移说明、已知限制、回退或恢复办法、上架检查结果以及发布状态。

涉及数据库迁移时，先验证备份与恢复；不要承诺旧安装包一定能读取新数据库。部署和提审按用户在当前会话中的授权范围执行，准备工作可先完成。
