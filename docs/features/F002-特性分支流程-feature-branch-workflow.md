# F002：特性分支开发流程

- 创建日期：2026-10-29
- 授权来源：用户要求“有新的需求需要新建特性，然后在特性分支开发，然后测试完毕再合并到主分支”。
- 状态：[功能任务台账](README.md)

## 1. 目标与范围

新需求先登记功能编号和功能文档，再从最新 `main` 创建与功能编号对应的特性分支。开发、缺陷修复、测试和文档更新均在该分支完成；适用测试通过且报告、台账更新后，才能合并到 `main`。

本次只建立项目工作流约束和文档规则，不新增 CI、分支保护、远程仓库权限或自动合并能力。

## 2. 验收标准

| 编号 | 场景 | 预期结果 |
|---|---|---|
| AC-01 | 收到新的产品需求 | 先分配或复用功能编号、建立功能文档并明确验收标准，再开始实现 |
| AC-02 | 开始实现新需求 | 从最新 `main` 创建 `feat/F编号-english-topic` 分支，不直接在 `main` 开发 |
| AC-03 | 特性分支准备合并 | 适用测试全部通过，没有验收阻塞问题，测试报告和功能台账已更新 |
| AC-04 | 测试失败、未执行或受阻 | 特性分支不得合并到 `main`，继续修复并重新验证 |
| AC-05 | AI 开发助手进入项目 | `AGENTS.md`、`CLAUDE.md` 和开发流程表达一致的分支与合并规则 |

## 3. 实现方案与任务

- [x] 在 `AGENTS.md` 写入新需求建档、特性分支和合并门禁规则。
- [x] 在 `CLAUDE.md` 同步代理工作约定。
- [x] 在开发流程增加分支准备阶段、分支命名和合并条件。
- [x] 建立 F002 功能登记和测试报告。
- [x] 验证三处规则一致、Markdown 链接有效且文档格式检查通过。

## 4. 验证方式

- 检索三份规则文档中的功能编号、分支格式、测试门禁和禁止直接在 `main` 开发等关键词。
- 检查项目内 Markdown 本地链接均指向实际文件。
- 执行 `git diff --check`，确认没有空白错误。
- 检查当前开发分支为 `feat/F002-feature-branch-workflow`。

## 5. 已知限制

当前规则依赖开发者和代理遵守，尚未通过托管平台分支保护或 CI 强制执行。远程合并权限、评审人数和自动化检查策略留待后续仓库治理需求决定。
